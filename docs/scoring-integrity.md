# ZxBench 判分可信度：全链路约束与发布闸门

单题误判不能只靠事后调正则修复。一次正式评测至少有五种相互独立的事实：冻结题目及约束、实际下发的提示、候选模型原始回答、可验证的执行/解析证据、Judge 判断。总分是这些事实的派生数据，不是比它们更高优先级的事实。

## 权威顺序

1. 题目、运行约束、评分配置和版本必须随运行冻结。运行时注入的 `ANSWER:`、JSON 等输出协议属于评分契约，不能在评价模型遵循性时被当成模型自创格式。
2. 原始回答及环境/工具轨迹不可覆盖。解析器只能生成派生字段；如果解析器升级，应从原始回答重放，并保留旧判分与变更理由。
3. 已验证的执行结果高于 Judge 对代码或命令的主观推断；Judge 可以标记冲突，不能静默推翻执行事实。纯语义任务或规则评分器的已知盲区才由 Judge 补判。
4. 环境故障、Judge 故障、候选输出错误必须分开记录。前两者不计为模型失败；存在未补判的题目不得宣布整轮评分完成。
5. 运行摘要和榜单只能从完整、可审计的题级记录生成。`status=completed` 只表示执行结束，不等于评分可信。

## 当前已落地

- 在线评分、保存答案补 Judge、冻结答案离线重算共用 `detectFormatBlindspot`，减少同一答案因路径不同产生的结果漂移。
- 质量审计检查 CLI 解析漏判、单次评分历史与最终分数不一致、非法分数、Judge 分数缺少 Judge 记录。发现这些问题时 `scoringComplete=false`、质量等级为 critical。
- Judge 与已验证执行冲突、CLI 规则与 Judge 冲突分别留证并进入人工复核计数；未解决的冲突阻止正式发布，且不自动改写执行分数。
- 榜单排除已知 `scoringComplete=false` 的运行，详情仍可查看；前端明确提示评分未完成或完整性异常。
- 冻结运行重算先只读预演，核验题目/结果一一对应；应用时备份 SQLite 并事务写入。重复执行没有变化时不再备份和写入。

## 下一阶段发布标准

以下工作尚未自动化，不能把当前闸门误称为彻底解决所有历史误判：

- **契约一致性**：在正式运行前检查题目要求、运行级提示、评分器和 Judge rubric 的格式约束是否一致；把实际发送的完整提示摘要/哈希存入每题审计记录。
- **独立交叉验证**：对 `ANSWER:` 包装、拒答、引用危险命令、等价命令、代码块、多候选答案做变形测试；解析器不应因无关包装改变语义结论。对高风险零分、满分和规则/Judge 大幅分歧做抽样人工金标。
- **可重放性**：每个评分器发布时声明所需证据。文本评分器可由冻结回答重放；依赖 sandbox/工具状态的评分器必须保留执行轨迹或重新执行，不能从答案文本伪造“重新判分”。
- **历史回填**：旧运行未保存完整质量报告或缺少运行时提示证据时，榜单仍可能把它们当作合格运行；应分批回填审计状态，并将“未审计”与“审计通过”分开展示。不同题包/协议版本不得直接同榜比较。
- **持续监控**：统计环境故障、Judge 失败、解析漏判、分数漂移、未测量约束、规则/Judge 冲突的比率；部署新评分器前用历史冻结答案做影子重算，公布分数变化清单及原因，再决定是否升级正式口径。

发布原则：没有完整题级覆盖、可复现的评分依据和通过的质量审计，就只能展示“暂定结果”，不能把一个总分当成正式能力结论。
